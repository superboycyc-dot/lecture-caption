# Developer ID release checklist

Current public releases remain ad-hoc signed until a **new version** passes every check below. Do not overwrite their assets or claim notarization based on certificate availability alone.

1. Account holder signs into Xcode Settings → Accounts, selects the paid team, and creates **Developer ID Application** in Manage Certificates. Do not commit/export the private key or copy Apple credentials into chat.
2. Set `LECTURE_CODESIGN_IDENTITY` to the local Developer ID Application certificate name or its public SHA-1 identity fingerprint. Run `python scripts/build_app.py`. PyInstaller signs collected code with Hardened Runtime; native tools use the same identity and secure timestamp. Entitlements retain audio access and unsigned executable memory for ctypes/libffi callbacks; no debugger or disabled library-validation entitlement is enabled on the main app. The Qt WebEngine helper is separately signed with Qt’s bundled upstream entitlements as required by https://doc.qt.io/qt-6/qtwebengine-deploying.html; only that helper receives Chromium’s JIT/library-validation/page-protection exceptions. Enclosing framework and app resource seals are then refreshed.
3. Create an app-specific password through the account holder's Apple Account if using Apple-ID notarization. In a private local Terminal, run `xcrun notarytool store-credentials lecture-caption-notary` and answer Apple's interactive prompts. The password stays in Keychain and must never be passed through chat, agent tool arguments, or GitHub plaintext files.
4. Run `python scripts/notarize_app.py --profile lecture-caption-notary`. This reads only the profile name; Apple's tool accesses its Keychain credential. It requires Developer ID, runtime and timestamp, saves the submission ID immediately, waits for Accepted, staples the ticket and checks Gatekeeper. If waiting times out, resume with `--submission-id` instead of re-uploading. No public release before all succeed.
5. Test the signed bundle's UI with isolated synthetic data, microphone permission bridge, Apple services, PDF math and updater. A real microphone/system-audio test needs explicit authorized test content. Preserve user data and avoid reading real keys or personal recordings/notes.
6. After stapling, create the final ZIP and SHA256SUMS. Open a PR, wait for CI and tag the exact version. Publish **the notarized local artifact**, not the current ad-hoc GitHub runner rebuild. The existing release workflow must be changed/gated before pushing that release tag. Its present CI does not possess an Apple identity or notary profile.
7. Download the public ZIP, verify checksums, Developer ID/Team ID, stapled ticket, Gatekeeper acceptance and launch. Only then update download instructions to remove the older Open Anyway workaround from the primary path. Ordinary downloaded-app and privacy permission confirmations may still appear.

Certificate owner / team identity will be visible in the software signature. Code authorship and MIT licensing remain separate. This does not submit the app to the Mac App Store.
